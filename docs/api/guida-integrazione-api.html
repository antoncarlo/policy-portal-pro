Guida definitiva integrazione API real-time

Portale Mariano → Tecno Advance MGA

Questo documento descrive l'integrazione webhook real-time tra il portale esterno e il backend di Tecno Advance MGA Broker S.r.l. per la trasmissione automatica delle pratiche assicurative al momento del salvataggio. I contenuti riflettono il comportamento effettivo dell'endpoint in produzione.

1Obiettivo dell'integrazione

Al salvataggio di una pratica nel portale Mariano, il sistema deve inviare in tempo reale i dati del cliente e della pratica (con gli eventuali allegati) all'endpoint webhook di Tecno Advance MGA tramite una singola chiamata HTTP autenticata. Ogni chiamata valida crea una nuova pratica in stato in_lavorazione.

ParametroValoreAutenticazione
Base URL https://policy-portal-pro.vercel.app —
Endpoint https://policy-portal-pro.vercel.app/api/webhook-receive-policy X-API-Key + Firma HMAC
Metodo POST —
Formato application/json (UTF-8) —
Trigger Salvataggio pratica (real-time) —

3Header obbligatori

Ogni richiesta POST all'endpoint deve includere i seguenti header. La firma HMAC è obbligatoria per il superamento della validazione. Non è previsto né richiesto alcun header timestamp.

HeaderObbligatorioDescrizione
Content-TypeSìSempre application/json
X-API-KeySìChiave API assegnata al portale mittente
X-SignatureSìFirma HMAC-SHA256 del body nel formato sha256=<hex>
X-Idempotency-KeyNoChiave di idempotenza. In alternativa si può usare il campo idempotency_key nel body

4Firma HMAC

La firma garantisce autenticità e integrità del payload. Si calcola come HMAC-SHA256 sul body JSON esatto della richiesta, usando il WEBHOOK_SECRET come chiave, e si invia in formato esadecimale con prefisso sha256= nell'header X-Signature.

  • La firma copre solo il body: nessun timestamp, nessun header aggiuntivo nella stringa firmata.
  • Il server ricalcola la firma su JSON.stringify(body): firma e invia la stessa identica stringa JSON compatta (senza spazi superflui, stesso ordine dei campi) per garantire la corrispondenza.
  • Il confronto lato server avviene in constant time; una firma non valida restituisce 401.
Node.js 
const crypto = require('crypto');

const API_KEY = 'tmga_ba098bcfeabe1092852fbd6f3ef29b14';
const WEBHOOK_SECRET =
  'tmga_whsec_00d692766b535ffb049ec797b93decc6cbe67568882ea1975f20c512d5fab875';
const URL = 'https://policy-portal-pro.vercel.app/api/webhook-receive-policy';

const payload = {
  source: 'portale-mariano',
  practice_type: 'rc',
  client_name: 'Mario Rossi',
  client_email: 'mario.rossi@example.com',
  client_phone: '+39 333 1234567',
};

// Firma la STESSA stringa che invii nel body (JSON compatto)
const rawBody = JSON.stringify(payload);
const signature = 'sha256=' + crypto
  .createHmac('sha256', WEBHOOK_SECRET)
  .update(rawBody, 'utf8')
  .digest('hex');

await fetch(URL, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-API-Key': API_KEY,
    'X-Signature': signature,
    'X-Idempotency-Key': 'MRN-2026-000123',
  },
  body: rawBody,
});

7Regola real-time al salvataggio

⚠️

Invio obbligatorio in tempo reale.Ogni operazione di salvataggio della pratica nel portale Mariano deve generare immediatamente la chiamata webhook corrispondente. Non è ammesso invio batch differito o manuale.

Evento nel portaleAzione richiestaEsito lato MGA
Nuova pratica salvataPOST webhook con dati completi + eventuali allegatiCrea una nuova pratica in stato in_lavorazione
Reinvio della stessa praticaPOST con la stessa X-Idempotency-Key / idempotency_keyNessun duplicato: ritorna la pratica esistente con duplicate: true
Pratica con documentiPOST con array documents[] valorizzatoI file vengono caricati nello storage e collegati alla pratica
⚠️

Nota sul comportamento.L'endpoint non gestisce operazioni di aggiornamento o annullamento: ogni chiamata valida priva di idempotency key già nota crea una nuova pratica. Per evitare duplicati nei retry, riusa sempre la stessa chiave di idempotenza.

8Risposte attese

In caso di acquisizione corretta l'endpoint risponde con 200 OK e un corpo JSON di conferma contenente l'identificativo interno e il numero pratica assegnato (formato PR-YYYY-NNNN).

✅

200 OK — Pratica creata correttamente.La presenza di "success": true conferma l'acquisizione. Salvare practice_id e practice_number per riconciliazioni successive.

Risposta di successo

JSON 
{
  "success": true,
  "practice_id": "8f3a2c91-d4e7-4b6a-9c12-7e5f0a1b2c3d",
  "practice_number": "PR-2026-1234",
  "message": "Pratica creata con successo."
}

Risposta su chiave di idempotenza già vista

JSON 
{
  "success": true,
  "practice_id": "8f3a2c91-d4e7-4b6a-9c12-7e5f0a1b2c3d",
  "practice_number": "PR-2026-1234",
  "message": "Pratica già esistente (idempotency key riconosciuta).",
  "duplicate": true
}

Le risposte di errore hanno sempre la forma { "error": "..." }, con campi aggiuntivi a seconda del caso (es. missing_fields, valid_types, missing, allowed_types, retry_after).

9Retry e idempotenza

La chiave di idempotenza si fornisce tramite l'header X-Idempotency-Key oppure il campo idempotency_key nel body. Reinvii con la stessa chiave non generano duplicati: l'endpoint restituisce la pratica già creata con 200 e duplicate: true.

ScenarioStrategia
Timeout o nessuna rispostaRetry con backoff esponenziale: 1s, 2s, 4s, 8s, 16s (max 5 tentativi), riusando la stessa chiave di idempotenza
Risposta 500 / 503Retry con backoff esponenziale, stessa chiave di idempotenza
Risposta 429Attendere e ritentare rispettando l'header Retry-After
Risposta 200 con duplicate: truePratica già acquisita: interrompere i retry
Risposta 401 (firma)Errore di firma: ricalcolare l'HMAC sul body esatto inviato, non ritentare in loop
Risposta 422Errore permanente di validazione: correggere i campi indicati in error, non ritentare invariato
Reinvio della stessa praticaMantenere identica la X-Idempotency-Key per garantire l'idempotenza

12Nota di sicurezza

⚠️

Trattamento delle credenziali.La X-API-Key e il WEBHOOK_SECRET sono segreti riservati. Devono risiedere esclusivamente nel backend del portale mittente, archiviati come variabili d'ambiente o in un secret manager. Non vanno mai inseriti nel codice frontend, in URL, in log, in messaggi email in chiaro o in repository pubblici.
